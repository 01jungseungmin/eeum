현재 브랜치의 변경사항을 분석해서 PR 본문과 Worklog를 작성하세요.
사용자 요청에 이슈 번호가 있으면 PR에 연결한다(예: `$pr 42`).

## 컨텍스트 수집 (먼저 실행)

아래 명령을 직접 실행해 결과를 수집한다.

```bash
git branch --show-current
git log develop..HEAD --oneline
git diff develop...HEAD --stat
```

변경 통계는 필요한 마지막 20줄만 확인한다.

## 작성 절차
1. 위 커밋/변경 통계로 작업 범위를 파악한다
2. 핵심 변경 파일 2~3개만 diff를 확인해 "무엇을 왜 바꿨는지" 파악한다 (전체 diff를 읽지 않는다)
3. 아래 형식으로 PR 본문을 작성한다
4. 마지막에 Worklog 항목을 작성한다

## PR 본문 형식

```markdown
## 🔗 관련 이슈
- closes #{이슈번호}

## 📌 작업 내용
- {변경 사항을 커밋 단위가 아닌 기능 단위로 묶어서 서술}
- {왜 이렇게 구현했는지 설계 의도가 드러나게}

## 🧪 테스트
- [ ] 단위 테스트 추가/수정: {테스트 클래스명}
- [ ] `./gradlew test` 통과 확인
- {동시성/멱등성 관련이면 해당 STP 시나리오 검증 여부}

## 💬 리뷰 포인트
- {리뷰어가 집중해서 봐야 할 부분 1~2개}
- {스스로 확신이 없거나 트레이드오프가 있었던 결정}

## 📎 참고 사항
- {DB 스키마 변경, 환경변수 추가, 마이그레이션 필요 여부 등 머지 시 주의사항}
```

## Worklog 형식 (PR 본문 뒤에 별도 출력)

```markdown
### {YYYY-MM-DD} — {브랜치명}
- 작업: {한 줄 요약}
- 구현: {핵심 구현 내용 2~3줄}
- 이슈/배운 점: {막혔던 부분, 해결 방법, 다음에 참고할 내용}
- 남은 작업: {이 PR에 포함하지 않은 후속 작업}
```

## 작성 규칙
- PR 제목 제안: 커밋 컨벤션과 동일하게 `feat: {요약}` / `fix:` / `refactor:` + 한글
- 작업 내용은 diff 나열이 아니라 의도 중심 서술 — "OrderService 수정"(나쁨) vs
  "주문 만료와 결제 Webhook 경쟁 방지를 위해 상태 조건부 UPDATE로 변경"(좋음)
- 리뷰 포인트는 반드시 작성 — 비어 있으면 리뷰어가 어디를 봐야 할지 모른다
- 테스트 체크박스는 실제 테스트 파일 존재 여부를 확인 후 체크 상태를 결정한다
