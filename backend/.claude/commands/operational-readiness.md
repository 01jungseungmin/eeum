`$ARGUMENTS`의 변경사항, 도메인 또는 운영 시나리오에 대해 운영 준비도를 점검하세요.
인자가 없으면 현재 브랜치 변경사항과 운영 구성을 대상으로 점검합니다.

## 목적과 경계

이 커맨드는 "장애가 나면 고객·운영자·데이터가 어떻게 되는가"를 코드와 설정, 문서에서 추적하여 운영 위험 레지스터를 작성한다. 단순 코드 스타일·레이어 리뷰는 담당하지 않는다.

다음에 사용한다.

- 결제·환불·정산·원장·가격/수수료 변경
- 외부 API, Redis, DB, 메시징, 파일 저장소, 인증 연동의 추가·변경
- 배포 구성, 환경 설정, 스케줄러, 비동기 풀, 데이터 마이그레이션 변경
- 장애·데이터 불일치·CS 사건의 사후 분석 및 재발 방지 점검
- 출시·대규모 행사 전에 운영 준비 상태를 확인할 때

사용자의 승인 없이 프로덕션 설정, 외부 시스템, 운영 데이터는 변경하지 않는다. 법률·세무·계약상 의무는 코드만으로 판정하지 말고 "정책/법무 확인 필요"로 명확히 분리한다. 확인하지 못한 사항을 충족했다고 추정하지 않는다.

## 선행 읽기와 범위 설정

1. `.claude/CLAUDE.md`를 읽고 프로젝트 규칙을 적용한다.
2. `.claude/skills/references/operational-readiness.md`를 처음부터 끝까지 읽는다.
3. 대상이 결제·정산·PortOne이면 `references/payment-settlement.md`를 반드시 읽는다.
4. 스레드, 커넥션, 소켓, 스케줄러, 비동기 풀을 다루면 `references/resource-budget.md`를 읽는다.
5. 외부 공개 API·Webhook이면 API 계약과 공식 문서를 현재 시점에 대조한다. 구현 변경이 포함될 때만 `review-api-contract` 또는 계약 테스트를 후속 작업으로 연결한다.
6. 배포·컨테이너·CI를 점검하면 backend 밖의 저장소 루트도 확인한다: `../docker-compose.prod.yml`, `../Dockerfile`, `../.github/workflows/backend-ci.yml`. 이 파일을 읽지 않고 배포 구성 확인 불가로 결론 내리지 않는다.

대상 범위를 먼저 선언한다. 변경사항이 주어졌다면 diff만 보지 말고 호출 흐름, 설정 파일, 관련 스케줄러, 실패 기록/재처리 경로까지 추적한다. 전체 시스템 감사를 요청받은 경우에는 도메인별로 나누어 근거를 수집하며, 읽지 않은 영역은 미점검으로 남긴다.

## 점검 방법

각 의존성과 운영 흐름에 아래 다섯 질문을 동일하게 적용한다.

1. 느려지면 요청 스레드, 큐, DB 트랜잭션, 고객 화면은 어떻게 되는가?
2. 죽거나 연결이 끊기면 기능은 실패·지연·열화 중 어느 상태가 되는가?
3. 잘못되거나 오래된 응답이면 내부 상태를 어떻게 검증·격리하는가?
4. 같은 요청·이벤트·운영 조치가 중복되면 무엇이 한 번만 처리됨을 보장하는가?
5. 복구 뒤 밀린 요청·outbox·Webhook·배치를 어떻게 대사하고 재처리하는가?

다음 축을 빠뜨리지 않는다. 모든 축이 이번 범위에 해당하지 않을 수 있으므로, 해당 없음의 근거도 남긴다.

- 외부 의존성 및 공급자 한도·계정·장애 공지 경로
- 돈과 원장: 승인/취소/환불/수익/지급의 대사, 격리, 수동 수습, 감사 이력
- 관측성: 구조화 로그·traceId, 기술 지표와 업무 지표, 알림 임계값과 담당자
- 배포와 변경: 무중단/종료 대기, 롤백, 마이그레이션 잠금, 설정값 변경 이력
- 용량과 자원: 요청/DB/Redis/비동기/장기 연결 예산과 피크 시나리오
- 백업과 복구: 백업 범위, 복원 훈련, RPO/RTO, 재처리 가능한 데이터 범위
- 보안·개인정보: 로그 마스킹, 비밀값 교체, 관리자 접근·감사·권한 회수
- CS와 운영 절차: 고객 조회 화면, 안내 문구, 기능 차단 기준, 사고 지휘·연락망

## 근거와 심각도

각 결론에는 파일 경로와 설정 키, 코드 위치, 테스트/운영 문서 또는 "확인 불가" 중 하나를 근거로 남긴다. 설정 파일에 없는 프레임워크 기본값은 실제 버전의 기본값임을 확인하기 전에는 단정하지 않는다.

- Critical: 금전 손실·개인정보 유출·원복 불가능한 데이터 손상 또는 전체 서비스 장기 중단 가능성
- Major: 고객 거래가 막히거나 잘못된 상태가 누적되며, 수동 수습이 필요하지만 통제 경로가 불완전함
- Minor: 장애 탐지·복구 시간이 불필요하게 길어지거나 운영 부담이 커지는 결함
- 확인 필요: 정책, 인프라 계정, 공급자 계약, 실제 배포 환경처럼 저장소 근거만으로 판정할 수 없음

문제가 있다고 해서 즉시 코드 수정안을 확정하지 않는다. 고객/원장 상태 전이 또는 운영 권한을 바꾸는 선택지는 정책 결정이 필요한지 구분하고, 필요한 경우 사용자에게 선택지를 제시한다.

## 출력 형식

아래 순서로 보고한다. 근거 없는 일반론이나 체크리스트 나열로 끝내지 않는다.

1. **범위와 결론** — 점검 범위, 점검하지 못한 범위, 출시/변경 전 차단해야 할 Critical·Major 요약
2. **시나리오 판정** — 범위에 관련된 이음 시나리오 카탈로그의 각 O-ID를 `점검`, `해당 없음(근거)`, `미점검` 중 하나로 한 줄씩 남긴다.
3. **위험 목록** — 아래 둘 중 범위에 맞는 형식 하나만 선택해 출력한다.
   - **변경 점검**(파일·기능 범위가 좁을 때): 표 형식 `ID, 심각도, 시나리오, 근거, 조치`. 소유자·상세 Runbook을 추정으로 채우지 않는다.
   - **전체 감사**(전체 시스템·출시 준비 요청일 때): 위험마다 세로 카드로 고객·데이터 영향, 현재 방어/근거, 감지, 즉시 완화, 영구 조치, 소유자 또는 확인 필요를 쓴다.
4. **복구·대사 흐름** — 돈 또는 상태 변경이 있으면 정상 흐름과 복구 후 대사/재처리 기준을 적는다. 재처리 키, 멱등성 기준, 격리 상태의 해제 주체를 명시한다.
5. **관측성과 Runbook 공백** — 추가해야 할 지표/알림, 첫 15분 조치, 운영자 권한·감사 이력 공백
6. **검증 가능한 후속 작업** — 작업마다 완료 조건을 쓴다. 코드, 테스트, 대시보드, 복원 훈련, 정책 결정/법무 확인을 구분한다.

통과 판단이 필요하면 아래 중 하나만 사용한다.

- `출시 차단`: Critical 또는 미해결 Major가 있음
- `조건부 진행`: 위험 수용 주체·기한·완화책이 기록된 Major만 남았거나, 담당자·기한을 받지 못한 `확인 필요` 항목이 남음. 후자의 항목은 결론에 명시한다.
- `운영 준비`: 범위 내 Critical/Major가 없고, 확인 필요 항목의 담당자와 기한이 기록됨

위험 수용 주체, 기한, 담당자는 사용자 또는 조직의 운영 기록에서만 받는다. 근거 없이 추정하지 않으며, 받지 못한 Critical/Major는 `출시 차단`으로 둔다.

## 담당하지 않는 일

- 실제 장애 대응을 대신해 프로덕션 조치를 실행하지 않는다.
- 법적 보존 기간, 환불 기한, 세무 의무를 추측해 확정하지 않는다.
- 증거 없이 특정 벤더, 클라우드 구성, 모니터링 제품 도입을 처방하지 않는다.
- 기존 전문 Skill의 상세 코드 리뷰를 중복하지 않는다. 발견 사항은 적절한 Skill과 파일 경로로 연결하되, 운영 영향과 복구 관점은 이 커맨드가 통합해 보고한다.
