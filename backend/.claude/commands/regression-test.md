$ARGUMENTS 에 기술된 버그(또는 직전 대화에서 진단한 버그)에 대한 회귀 테스트를 작성하세요.

## 목적

리뷰와 자원 테스트는 **발견**을 담당한다. 이 커맨드는 **재발 방지**를 담당한다.

발견된 버그는 반드시 "먼저 실패하는 테스트"로 고정한 다음 고쳐야 한다.
테스트 없이 고치면 (1) 정말 고쳐졌는지 확인할 수 없고, (2) 나중에 리팩토링하다 조용히 되돌아온다.

## 입력이 부족할 때

버그를 재현 테스트로 옮기려면 아래가 필요하다. 없으면 **추측해서 만들지 말고 무엇이 없는지 먼저 묻는다.**

- 증상 (무엇이 잘못 동작하는가)
- 트리거 조건 (어떤 요청/타이밍/동시성에서)
- 결함 위치 (파일:라인)
- 기대 동작 (무엇이 맞는가)

## 작업 절차

1. 결함 위치의 코드를 읽고, **왜 그 코드가 증상을 만드는지** 인과를 한 문단으로 정리한다. 이 정리가 곧 테스트의 주석이 된다.
2. 그 인과를 재현하는 데 **최소한으로 필요한 것**을 판단해 테스트 유형을 고른다:

   | 결함의 성격 | 테스트 유형 | 위치 |
   |---|---|---|
   | 순수 분기/조건/계산 오류 | 단위 (Mockito) | 프로덕션과 동일 패키지 |
   | catch 타입, 예외 전파, 이벤트 발행 여부 | 단위 (Mockito) | 동일 |
   | 영속성 컨텍스트, FK, 실제 쿼리 결과 | Testcontainers 통합 | 동일 |
   | 스레드, 커넥션 풀, 소켓, 비동기 풀 | 자원 통합 (`resource-test` 템플릿) | 동일 |
   | 코드 패턴 자체를 금지하고 싶은 경우 | ArchUnit (`arch-rules`) | `architecture/` |

   **가장 가벼운 유형을 고른다.** 단위 테스트로 재현되는 버그를 Testcontainers로 만들면 CI만 느려진다.
   반대로, Mocking하면 재현이 사라지는 버그(자원 계열)를 단위 테스트로 만들면 **아무것도 검증하지 못하는 테스트**가 된다. 이 구분이 이 커맨드의 핵심이다.

3. 테스트를 작성하고 **프로덕션 코드를 고치기 전에 실행해서 실패하는 것을 확인한다.**
   실패하지 않으면 재현에 실패한 것이다 — 테스트를 통과시키지 말고, 재현 조건을 다시 잡는다.
4. 실패 로그(예외 타입, 메시지, 스택 상단)를 기록한다. 이게 "이 테스트가 무엇을 잡는지"의 증거다.

## 작성 컨벤션

- 유형별 컨벤션은 각각 `test-gen`(단위) / `integration-test`(영속성) / `resource-test`(자원)를 따른다. 이 커맨드는 유형 선택과 재현 검증만 추가한다.
- 클래스 Javadoc에 반드시 넣는다:
  - 증상 한 줄
  - 결함 위치 (`파일:라인`)
  - 인과 설명 (절차 1에서 정리한 것)
  - 이 테스트가 고정하는 기대 동작
- 메서드명은 **버그가 아니라 기대 동작**으로 쓴다.
  - 나쁨: `SSE_전송이_요청_스레드를_블로킹한다()`
  - 좋음: `죽은_SSE_연결이_있어도_알림_생성_API는_3초_안에_응답한다()`
  - 이유: 버그가 고쳐진 뒤에도 이름이 계속 유효해야 한다.
- 회귀 테스트는 별도 패키지로 격리하지 않는다 — 해당 기능의 테스트와 같은 곳에 둔다. 격리하면 기능을 고칠 때 아무도 안 본다.

## 여러 결함을 한 번에 받은 경우

- 결함 하나당 테스트 메서드 하나로 분리한다. 묶으면 실패 시 원인을 특정할 수 없다.
- 심각도 순이 아니라 **재현 난이도가 낮은 순**으로 작성한다. 재현되는 것부터 확보하는 게 안전하다.
- 재현 자체가 불가능한 결함(예: 30분 타임아웃, 프록시 idle cut 같은 시간 축 문제)은 억지로 만들지 않는다. **재현 불가로 분류하고 대안**(모니터링 지표, 수동 소크 테스트 절차)을 제안한다.

## 금지 사항

- 프로덕션 코드를 수정하지 않는다 — 이 커맨드는 테스트만 만든다. 수정은 별도 요청으로 진행한다.
- 테스트를 통과시키기 위해 기대값을 실제 동작에 맞추지 않는다. 기대값은 **올바른 동작** 기준으로 쓴다.
- 실패하는 회귀 테스트에 `@Disabled`를 붙이지 않는다.
- 재현되지 않는데 "아마 이럴 것"이라며 테스트를 남기지 않는다 — 재현 실패로 보고한다.

## 출력 형식

1. 결함별 인과 정리 (한 문단씩)
2. 선택한 테스트 유형과 그 이유 — 특히 왜 더 가벼운 유형으로는 재현이 안 되는지
3. 생성한 파일 경로와 메서드 목록
4. **수정 전 실행 결과** — 실패 여부와 실패 로그 요약 (재현 성공의 증거)
5. 재현 불가로 분류한 결함과 대안 검증 방법
