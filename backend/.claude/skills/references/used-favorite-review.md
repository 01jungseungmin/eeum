# 중고거래·찜 교차 도메인 리뷰 불변식

중고거래(`used`) 또는 다형성 찜(`favorite`) 변경을 리뷰할 때 적용하는 공통 기준이다.
한 파일의 로컬 정합성만 보지 말고 Account, Store, Report, 관리자 조치, 운영 DDL과
테스트까지 같은 기능 흐름으로 연결한다.

## 적용 범위

다음 중 하나라도 변경되면 이 문서를 읽고 관련 진입점을 모두 추적한다.

- `api/used`, `application/used`, `domain/used`
- `api/favorite`, `application/favorite`, `domain/favorite`
- 중고글을 대상으로 하는 신고·관리자 조치
- 회원 탈퇴/정리와 중고글·찜의 연계
- `favoriteCount`, `viewCount`, 이미지 대표/순서 카운터
- 관련 `SecurityConfig`, 운영 DDL, 단위·통합·동시성 테스트

`Favorite`는 STORE와 USED_PRODUCT를 함께 다루므로 한 타입의 변경도 다른 타입에 대한
회귀를 만들 수 있다. switch 분기, 공용 DTO, 공용 삭제·카운트 메서드는 두 타입을 모두 본다.

## 공개 상태 불변식

### UsedProduct

- 공개 목록·비소유자 상세·공개 찜 수·신고 생성·찜 등록은 `deletedAt IS NULL`이고
  `hidden = false`인 게시글만 허용한다.
- 숨김 게시글은 작성자 상세와 관리자 처리처럼 명시적으로 허용된 경로에서만 보인다.
- 비소유자의 숨김 게시글 접근은 존재 여부가 드러나지 않도록 NOT_FOUND로 통일한다.
- 찜 해제·내 데이터 정리처럼 비공개 전환 뒤에도 필요한 쓰기는 허용하되, 응답에서
  비공개 대상의 이름·상태·카운터를 새로 노출하지 않는다.

### Store

공개 상점은 아래 조건을 모두 만족해야 한다.

- 상점 계정 `AccountStatus.ACTIVE`
- 점주 승인 `ApprovalStatus.APPROVED`
- 상점 상태가 `StoreStatus.SUSPENDED`가 아님

상점 상세, 찜 등록, 찜 목록, 공개 찜 수가 같은 조건을 사용해야 한다. 공개 필터는
메모리가 아니라 DB의 pagination/count 전에 적용한다. 기존 찜 삭제는 공개 여부와 무관하게
허용하되 비공개 대상 정보를 응답하지 않는다.

## API·페이징 불변식

- Controller의 PathVariable/RequestParam 식별자는 `@Validated`와 `@Positive`를 함께 적용한다.
- 컬렉션 요청은 컨테이너뿐 아니라 요소의 `@NotNull`, `@Valid`, 범위도 검증한다.
- Swagger의 인증 요구, 필드 의미, 최대 개수, 경로는 SecurityConfig와 런타임 동작에 맞춘다.
- 공용 DTO의 필드를 특정 도메인이 무시하면 전용 DTO로 분리하거나 실제로 지원한다.
- 필터는 Page/Slice 생성 전에 적용한다. 조회 후 메모리 필터링으로 페이지 크기,
  `totalElements`, `hasNext`를 왜곡하지 않는다.
- 실제 적용 정렬과 응답 `Pageable` 메타데이터를 일치시킨다. 정렬을 고정한다면 요청 sort를
  그대로 반환하지 않는다.
- 새 행이 목록 맨 앞에 꽂히는 무한 스크롤(최신순 정렬)은 OFFSET을 쓰지 않고 커서(keyset)로
  넘긴다. OFFSET은 페이지 사이 삽입 한 건에 목록 전체가 밀려 경계 항목이 중복되거나
  누락된다 — tie-break 정렬은 동률만 해결할 뿐 이 밀림을 막지 못한다. 커서는 정렬 키를
  전부 담는다(`createdAt`만 담고 PK를 빼면 같은 시각 행에서 같은 결함이 재현된다).
- 커서 목록은 `Slice`가 아니라 `CursorSlice`로 돌린다. 페이지 번호가 없는 계약에 `number`,
  `first`를 실으면 두 번째 페이지도 첫 페이지로 보고된다. 다음 커서는 서버가 만들어
  응답에 싣고(`nextCursorValue`/`nextCursorId`), 클라이언트는 그대로 되돌려보낸다 —
  정렬 키마다 값 형식이 다르므로 조립 규칙을 클라이언트에 넘기지 않는다.
- 카운터를 변경한 응답은 변경 후 값을 반환한다. bulk update 뒤 같은 엔티티를 사용할 때는
  영속성 컨텍스트 refresh/clear 여부를 확인한다.
- 기존 공개 계약을 바꾸면 사용자가 승인한 변경인지, 호환 경로나 동시 배포가 필요한지 분리한다.

## 쓰기·잠금 불변식

회원 상태와 대상 상태를 함께 바꾸는 인증 사용자 쓰기는 다음 순서를 기본으로 한다.

```text
actor Account → Store/UsedProduct → Favorite/UsedProductImage
```

- Account를 잠근 뒤 ACTIVE 상태를 다시 검증한다. 보안 필터를 통과했다는 사실만 믿지 않는다.
- 대상 행을 잠근 뒤 공개·숨김·삭제·소유권 상태를 다시 검증한다.
- Favorite나 Image를 대상 mutex보다 먼저 읽어 오래된 엔티티를 들고 기다리지 않는다.
- 여러 Store/UsedProduct를 잠글 때는 ID 오름차순처럼 하나의 전역 순서를 사용한다.
- OWNER 탈퇴, 회원 탈퇴, 관리자 조치, 신고 조치, 사용자 수정·삭제, 찜, 이미지 변경이
  같은 대상에 대해 같은 잠금 순서를 사용하는지 교차 확인한다.
- `@DynamicUpdate`는 서로 다른 컬럼의 stale overwrite만 줄인다. 상태 검증과 동일 필드 경합,
  check-then-act를 대신하지 않는다.

## 카운터·DB 불변식

- `(account_id, ref_type, ref_id)` UNIQUE를 엔티티와 운영 스키마 양쪽에 보장한다.
- 카운터 감소는 조회했던 과거 ID가 아니라 실제 삭제가 확정된 Favorite 행을 기준으로 한다.
- 조건부/원자 UPDATE의 영향 행 수가 0일 때 후속 카운터·응답 처리가 안전한지 확인한다.
- 전체 재계산은 실시간 add/remove/탈퇴와의 mutex 또는 명시적인 write-pause가 필요하다.
- 운영 DDL은 중복 정리 → UNIQUE/인덱스 생성 → 재계산 전체 구간의 쓰기 통제 조건을 명시한다.
- 엔티티 인덱스와 수동 DDL을 함께 확인한다. 실제 where/order by를 지원하는지는 MySQL
  `EXPLAIN` 확인 대상으로 표시한다.

## 이미지 불변식

- 추가·삭제·대표 변경은 모두 부모 UsedProduct 잠금을 먼저 획득한다.
- 최대 10장, `displayOrder` 유일성, 대표 이미지 최대 1장을 동시 요청에서도 유지한다.
- 요청 DTO의 대표 지정 필드가 실제 서비스 동작과 일치해야 한다.
- 삭제/숨김 게시글에 대기 중이던 이미지 쓰기가 뒤늦게 반영되지 않도록 잠금 뒤 상태를 재검증한다.

## 필수 교차 시나리오

정적 리뷰에서 아래 경쟁 순서를 직접 시뮬레이션한다.

- 탈퇴 ↔ 찜 등록/토글/직접 삭제
- 탈퇴 ↔ 중고글 생성/수정/이미지 변경
- 서로의 상점을 찜한 OWNER 동시 탈퇴
- STORE 공개 상태 변경 ↔ 찜 등록/목록/count
- 게시글 사용자 삭제 ↔ 찜 등록/직접 찜 삭제
- 신고 숨김·삭제 ↔ 사용자 수정·삭제·이미지 변경
- 이미지 동시 추가, 대표 변경 ↔ 삭제
- 관리자 전체 재계산 ↔ 실시간 찜 add/remove/탈퇴
- 조회수 bulk update ↔ 같은 영속성 컨텍스트의 응답 매핑

## 검증 게이트

- 단위 Mock 테스트만으로 JPA 1차 캐시, DB 락, UNIQUE, 실제 페이징을 통과 처리하지 않는다.
- 동시성 테스트는 단순 sleep/경과 시간 대신 barrier, latch, DB lock-wait처럼 경쟁 진입을
  결정적으로 증명한다.
- HTTP Validation·Swagger 계약은 Validator 또는 MockMvc 테스트로 고정한다.
- 사용자가 도메인 전체 탐색을 명시한 **전체 리뷰**에서만 이 문서의 모든 축을 다시 돈다.
  "전부 수정했어", "다시 봐줘", "최종 확인" 같은 수정 재리뷰는 `review-common.md`의
  범위 원장 안에서 관련 축만 다시 적용한다.
- 사용자가 승인하거나 보류한 항목은 별도 목록으로 유지한다. 승인 범위를 다른 계약으로 확대하지 않는다.
- 수정 재리뷰 중 범위 원장 밖의 Account·Store·Report 기존 문제를 발견해도 수정과 직접 관련이
  없으면 `범위 밖 기존` 비차단 항목으로 분리한다.
- 테스트를 실행하지 않았다면 정적 리뷰 통과와 런타임 검증 완료를 구분해 보고한다.
