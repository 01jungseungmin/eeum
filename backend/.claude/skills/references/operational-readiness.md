# 운영 준비도 점검 기준

`operational-readiness` 커맨드가 운영 위험을 일관되게 평가하기 위한 기준이다. 이 문서는 구현 상태를 주장하지 않는다. 현재 상태는 코드·설정·배포 문서·운영 담당자 확인으로 근거를 채운다.

## 증거 등급

| 등급 | 의미 | 예시 |
|---|---|---|
| E1 | 코드·테스트·설정으로 직접 확인 | timeout 설정, DB unique 제약, 재처리 테스트 |
| E2 | 배포/관측 설정 또는 운영 문서로 확인 | 대시보드, 온콜, 백업 정책, runbook |
| E3 | 담당자·공급자·법무 확인이 필요 | SLA, 실제 복원 이력, 보존/환불 법적 기준 |
| U | 근거 없음 또는 확인 불가 | "있을 것"이라는 추정 |

E1이 있다고 E2/E3이 자동으로 충족되는 것은 아니다. 예를 들어 retry 코드가 있어도 경보와 재처리 권한이 없으면 운영 복구는 미완성이다.

## 이음 의존성 목록

점검 시작 시 아래 목록을 기준으로 관련 없음도 판단한다. 새 의존성을 발견하면 후속 작업에 `의존성 목록 갱신 필요`로 남긴다.

| 의존성 | 대표 운영 경로 |
|---|---|
| PortOne | 주문·AI 플랜 결제 verify, Webhook, 취소·환불, 내부 결제 기록 대사 |
| MySQL | 주문·결제·정산 원장, HikariCP, 외부 DB 장애 조치와 백업/복원 |
| Redis | 분산 락, ShedLock `@SchedulerLock`, refresh/blacklist 토큰, Rate Limit, Webhook 중복 방지, 실시간 중계 |
| FCM·알림톡·Gmail SMTP | 도메인 이벤트/outbox 후 알림·메일 발송 |
| Kakao | OAuth 가입·로그인, 주소 좌표 변환(Geocoding) |
| 국세청 API | 사업자 등록 검증 |
| 공공데이터 API | AI 운영 위험 분석을 위한 지역 에너지·전력·가스사고 데이터 |
| Groq·Gemini | AI 기능 및 예약 메시지 |
| S3 | 이미지·첨부 파일 저장과 복구/수명 주기 |

## 이음 시나리오 카탈로그

아래 ID는 현재 구현의 안전성을 선언하는 목록이 아니라, 이음 운영 점검에서 반드시 호출 흐름과 수습 경로를 추적할 시나리오다. 변경 범위와 무관하면 해당 없음의 근거를 남긴다.

| ID | 반드시 추적할 경로 |
|---|---|
| O1 | 주문과 AI 플랜의 PortOne verify가 응답하지 않을 때 요청 스레드, Redis 락 유효 시간, DB 트랜잭션, 사용자 응답과 재시도 |
| O2 | 주문의 `OrderExpirationScheduler`와 AI 플랜의 `AiPlanPaymentExpirationScheduler`가 각각 15분 뒤 만료 처리한 후, PAID Webhook이 늦게 도착하는 상태 전이 |
| O3 | 부분 취소·늦게 발견된 원장·응답 유실 등 수동 검토/격리 건마다 조회, 사유·증빙, 승인, 재처리·해제 또는 환불 API/절차 |
| O4 | Redis 재시작·키 유실·복구 뒤 로그아웃 blacklist, refresh token, 분산 락, Webhook 중복 방지, Rate Limit, ShedLock `@SchedulerLock`의 고객 영향과 안전성. 주간 정산 마감·outbox 등 스케줄러가 멈추거나 중복 실행되는 경로를 포함한다. |
| O5 | 배포·재시작 중 처리하던 결제·취소 요청의 종료 대기, 클라이언트 재시도, Webhook 재전송과 중복 방지 |
| O6 | 월요일 00:00 Asia/Seoul 주간 정산 마감 실패, 부분 성공, 재실행, 누락 원장의 격리·수습 |
| O7 | 주문·AI 플랜의 PortOne 거래/취소 기록과 내부 결제·원장 기록을 비교하는 정기 대사, 불일치 알림과 종료 절차 |

실제 장애나 리뷰에서 새 운영 경로를 발견하면 후속 작업에 카탈로그 갱신 필요를 남긴다. 재현 가능한 결함은 `/regression-test`로 고정한다. 점검 중 이 기준 문서를 직접 갱신하지 않는다.

## 이음 배포 및 인스턴스 경계

backend 디렉터리만으로 배포 상태를 판단하지 않는다. 저장소 루트의 `../docker-compose.prod.yml`, `../Dockerfile`, `../.github/workflows/backend-ci.yml`를 함께 확인한다. 컨테이너 수, healthcheck, graceful shutdown, 로그 드라이버/보존, 이미지 빌드·배포 경로, CI 검증 범위를 근거로 기록한다.

인스턴스를 늘리거나 늘릴 계획이 있다면 다음을 별도로 점검한다.

- 전 인스턴스에서 한 번만 실행해야 하는 스케줄러는 분산 락 또는 명시적인 리더 선출을 가진다. 단, `@InstanceLocalSchedule`처럼 JVM 안의 SSE/WebSocket 세션을 다루는 작업은 모든 인스턴스가 실행되어야 한다.
- SSE/WebSocket 세션, 로컬 메모리 상태, Redis Pub/Sub가 인스턴스 증설·축소·재시작 뒤에도 세션 회수와 메시지 전달을 보장하는지 확인한다.
- 정산·만료·보존 시각은 서버, 컨테이너, DB, 스케줄러가 같은 시간대 기준을 쓰는지 확인한다. 이음의 주간 정산 기준은 `Asia/Seoul`이다.
- 결제·주문·상품 등록 등 고객 영향 기능을 독립적으로 차단하거나 읽기 전용으로 열화할 kill switch/feature flag가 있는지, 없다면 안전한 대체 절차가 있는지 확인한다.

## 외부 의존성 카드

의존성 하나마다 다음 내용을 기록한다.

| 필드 | 확인할 내용 |
|---|---|
| 소유자와 용도 | 서비스 담당자, 고객 영향 기능, 대체 가능 여부 |
| 호출 경계 | timeout, 연결/읽기 timeout, circuit breaker 또는 동시성 제한, 트랜잭션 밖 호출 여부 |
| 실패 정책 | fail-open/fail-closed, 고객 메시지, 기능 열화 또는 차단 기준 |
| 정확성 | 응답 서명/상태 검증, 중복 키, 순서 역전, 오래된 응답 처리 |
| 복구 | 재시도 한도·간격, DLQ/outbox, 재처리 명령자, 대사 기준 |
| 관측 | 성공률·지연·오류율, 공급자 상태 확인 경로, 경보 임계값 |
| 운영 | 계정 소유자, quota/비용 한도, 키 교체·계약/SLA·공지 채널 |

Redis는 단순 캐시인지 인증/락/멱등성의 진실 원천인지 분리해서 기록한다. 재시작·AOF 복구·복제 전환 뒤 키가 사라지거나 오래 남았을 때 로그인, 로그아웃, 락, 중복 방지가 각각 어떻게 변하는지 확인한다.

## 금전 및 상태 변경 흐름

결제, 환불, 취소, 수익 원장, 정산, 재고·예약처럼 되돌리기 어려운 상태에는 다음을 확인한다.

1. 요청 ID와 외부 거래 ID가 내부 레코드·감사 로그에 보존되는가?
2. 요청, 동기 verify, 비동기 Webhook, 재시도, 수동 조치가 같은 상태 전이 규칙을 따르는가?
3. 중복·역순·늦은 이벤트가 이전 상태를 되돌리거나 금액을 중복 반영하지 않는가?
4. 외부 승인과 내부 상태가 어긋났을 때 정기 대사가 이를 탐지하는가?
5. 격리 상태에는 조회, 담당자, 사유, 증빙, 승인, 재처리/해제 또는 환불의 종료 경로가 있는가?
6. 수동 조정은 실행자·승인자·전후 금액·사유·시각을 변경 불가능한 감사 이력으로 남기는가?

대사 작업은 단순 실패 재시도가 아니라 비교 대상, 시간 구간, 지연 허용 창, 불일치 상태, 중복 실행 방지, 통지, 수습 완료 기준을 가져야 한다.

## 관측성과 사고 대응

운영 알림은 "오류가 있었다"가 아니라 행동을 유발해야 한다.

- 기술 지표: 요청 오류율/지연, DB·Redis 연결, 큐·풀 포화, 스케줄러 지연, 배포 상태
- 업무 지표: 결제 성공률, verify/Webhook 지연, 대사 불일치, 격리·재처리 대기, outbox/DLQ 적체
- 상관관계: API 요청 ID, 외부 거래 ID, 주문/계정 ID는 민감 정보 없이 로그·추적·감사 이력에서 연결된다.
- 경보: 임계값, 중복 억제, 수신자, 1차 대응자, 미응답 escalation, 조용한 시간 정책을 확인한다.
- Runbook: 첫 15분의 확인 순서, 기능 차단 기준, 안전한 재처리 방법, 고객 공지/CS 이관, 사고 종료 조건, 사후 분석 담당자를 포함한다.

로그 보존량은 용량 숫자만 보지 말고 최대 트래픽에서의 실제 보존 시간, 중앙 수집 여부, 검색 권한, 개인정보 마스킹과 삭제 정책을 함께 확인한다.

## 배포·데이터·복구

배포와 DDL은 실패 자체보다 부분 적용과 복귀 불가 상태를 점검한다.

- 종료 신호부터 load balancer 제외, in-flight 요청 종료, 컨테이너 강제 종료까지의 시간을 확인한다.
- 배포 중 결제/주문 요청이 중단됐을 때 클라이언트 재시도와 Webhook 재전송이 중복을 만들지 확인한다.
- Flyway 등 마이그레이션은 예상 실행시간·잠금·대용량 테이블 영향·전방/후방 호환·롤포워드 계획을 확인한다.
- 설정값(수수료율, 한도, feature flag)은 변경자·승인자·적용 시각·이전 값·롤백 방법을 남긴다.
- 백업은 DB뿐 아니라 필요한 객체 저장소·설정·비밀 관리 구성도 범위에 포함한다. 복원 성공 여부는 최근의 실제 훈련 증거가 없으면 E3 또는 U다.
- RPO는 허용 가능한 데이터 유실 시간, RTO는 서비스 복구 목표 시간이다. 각각 기능과 데이터 종류별로 정하고, 복구 훈련 결과로 검증한다.

## 우선순위 결정 질문

위험을 발견하면 아래 순서로 판단한다.

1. 고객 돈·개인정보·원복 불가 데이터에 영향을 주는가?
2. 자동 감지 전에 고객/CS가 먼저 알아차릴 가능성이 있는가?
3. 안전한 자동 복구 또는 제한된 권한의 수동 수습 경로가 있는가?
4. 실제 부하·장애·복원 훈련으로 검증됐는가?
5. 위험 수용이 필요하다면 책임자, 만료일, 임시 완화책이 기록되는가?

1 또는 2가 `예`이고 3~5의 근거가 없으면 출시 차단 후보로 분류한다.
