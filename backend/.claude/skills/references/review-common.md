# 코드 리뷰 공통 규칙

이음(Eeum) 프로젝트 전문 코드 리뷰어 4종이 공유하는 공통 규칙이다.

- `review-security` — 권한/소유권
- `review-api-contract` — API 표준/DTO/계약
- `review-transaction` — 트랜잭션/이벤트/예외
- `review-persistence` — 엔티티/쿼리

각 리뷰어는 이 파일을 먼저 읽은 뒤 자신의 체크리스트만 적용한다.
심각도 기준과 출력 형식이 바뀌면 이 파일만 수정한다.

## 프로젝트 컨텍스트

- Java 17 / Spring Boot / JPA + QueryDSL / MySQL / Redis
- 패키지 구조는 `api / application / domain / infrastructure` 4-layer

## 운영 원칙

- 직접 코드를 수정하지 않는다.
- 파일을 수정하지 않는다.
- 리뷰 결과는 위반 사항과 수정 방향만 출력한다.
- 리팩토링 제안은 최소화하고, 표준 위반과 안정성 문제에 집중한다.
- 동작 변경을 수반하는 개선 제안은 "검토 필요"로 표시한다.
- 관련 없는 전체 코드베이스 탐색을 하지 않는다.
- 자신의 담당 영역이 아닌 위반은 보고하지 않는다 — 담당 리뷰어가 별도로 점검한다.
- 긴 코드 인용을 하지 않는다.
- 사용자가 바로 판단할 수 있도록 짧고 명확하게 출력한다.

## Bash 사용 제한

Bash는 아래 목적에만 사용한다.

- 변경 파일 확인
    - `git diff develop...HEAD --name-only`
    - `git diff --name-only`
    - `git diff --cached --name-only`
    - `git status --short`
- 필요 시 변경 내용 확인
    - `git diff develop...HEAD -- <file>`
    - `git diff -- <file>`
    - `git diff --cached -- <file>`

아래 명령은 사용하지 않는다.

- 파일 수정 명령
- 삭제 명령
- DB 명령
- 배포 명령
- 장시간 실행되는 전체 테스트
- `gradlew clean test`

테스트 실행은 사용자가 명시적으로 요청한 경우에만 수행한다.

## 리뷰 절차

1. 먼저 `git diff develop...HEAD --name-only`, `git diff --name-only`,
   `git diff --cached --name-only`, `git status --short`의 합집합으로 범위를 만든다.
   staged/unstaged/untracked 파일을 빠뜨리지 않는다.
2. 리뷰 시작 전에 아래 세 모드 중 하나를 선택하고 범위를 고정한다.
   - **변경 리뷰**: 최초 리뷰의 기본값. 위 합집합과 판단에 필요한 직접 의존만 본다.
   - **수정 재리뷰**: "전부 수정했어", "고쳤으니 다시 봐줘", "재리뷰"의 기본값. 이전 리뷰 범위,
     이전 지적, 그 지적을 고친 변경, 수정의 직접 호출자·경쟁 경로만 본다. "전부 수정"은
     "도메인 전체를 새로 리뷰"한다는 뜻이 아니다.
   - **전체 리뷰**: 사용자가 "도메인 전체", "처음부터 전체", "새 문제까지 전체 탐색"처럼
     범위 확대를 명시했을 때만 적용한다. "꼼꼼히", "최종", "다시 리뷰"라는 표현만으로
     수정 재리뷰를 전체 리뷰로 바꾸지 않는다.
3. 수정 재리뷰에서는 전문 리뷰어를 실행하기 전에 **범위 원장**을 만든다.
   - 이전 리뷰의 대상 파일·공개 진입점·쓰기 진입점
   - 이전 지적과 `해결 예정 / 사용자 승인 / 보류 / 제외` 상태
   - 수정 커밋 또는 현재 변경 파일
   - 수정 안전성을 판단하는 데 꼭 필요한 직접 호출자·경쟁 경로
   범위 원장 밖의 기존 코드는 수정의 안전성을 증명하는 데 필요한 만큼 읽을 수 있지만,
   그 코드의 독립적인 기존 문제를 차단 지적으로 승격하지 않는다.
4. 전체 리뷰 모드는 diff로 범위를 축소하지 않는다. 지정 도메인의 Controller, DTO, Service,
   Entity, Repository, SecurityConfig, 외부 Gateway, 스케줄러/복구 작업, 운영 DDL, 테스트까지
   진입점과 직접 의존을 추적한다.
5. 수정 재리뷰는 전체 체크리스트를 **고정된 범위 안에서만** 다시 적용한다. 새 지적에는 반드시
   아래 출처 중 하나를 붙인다.
   - `[잔존]`: 이전에 보고한 문제가 아직 해결되지 않음
   - `[회귀]`: 이번 수정이 새로 만든 문제
   - `[이전 누락]`: 이전의 고정 범위에 원래 있었지만 리뷰가 놓친 문제
   - `[범위 밖 기존]`: 수정과 무관한 기존 문제. 차단 지적과 분리한 비차단 참고 항목
   - `[정책 보류]`: 코드만으로 결론낼 수 없고 사용자 결정이 필요한 항목
   범위 밖에서 Critical 보안·데이터 손실 위험을 우연히 발견한 경우에만 `범위 밖 긴급`으로
   별도 보고하며, 이를 이유로 나머지 영역까지 조용히 확대하지 않는다.
6. 변경이 다른 타입을 함께 처리하는 공용 switch/다형성 참조/공용 DTO/카운터에 닿으면 모든 타입의
   경로를 함께 본다. 한 분기의 수정이 기존 분기에 만든 회귀를 확인한다.
7. 목록이 없으면 사용자가 지정한 파일과 도메인을 대상으로 한다.
8. 변경 파일 중 자신의 담당 영역을 읽고, 판단에 필요한 직접 의존 파일을 추가 확인한다.
9. 리뷰 시작 전에 담당 체크리스트의 점검 대상 목록을 만들고, 종료 전에 모든 항목의 확인 여부를
   대조한다. 확인하지 않은 항목이 있으면 통과 메시지를 출력하지 않는다.
10. 자신의 체크리스트 기준으로 위반과 추가 확인 필요 항목을 분리해 보고한다.

### 지적의 증거 기준

- 차단 지적은 `실행 가능한 진입점 → 선행 상태 → 경쟁/호출 순서 → 기존 방어가 실패하는 이유 →
  관찰 가능한 피해`를 코드로 설명할 수 있어야 한다.
- JPA·DB·동시성 지적은 트랜잭션 경계, 격리 수준, locking/current read 여부, flush/clear 시점,
  영향 행 수를 현재 구현과 연결한다. 일반론만으로 Critical/Major를 확정하지 않는다.
- 호출자가 없는 코드, 미배포 계약, 운영 적용 여부가 불명확한 DDL은 실행 가능성을 구분한다.
  확인되지 않은 조건은 `추가 확인 필요` 또는 `[정책 보류]`로 둔다.
- 테스트 부재만으로 프로덕션 결함을 단정하지 않는다. 이미 증명된 결함의 회귀 방지가 없으면 Minor,
  재현 테스트 없이는 사실 여부를 가를 수 없으면 `추가 확인 필요`로 보고한다.
- 심각도는 체크리스트 항목 이름이 아니라 현재 코드에서 실제로 가능한 피해를 기준으로 정한다.
  같은 원인의 불확실한 파생 시나리오를 별도 지적으로 부풀리지 않는다.
- 사용자가 정확한 전제와 잔여 위험을 이해하고 승인·제외한 항목은 그 전제가 바뀌거나 새 회귀가
  생기지 않는 한 다시 지적하지 않는다.

### 도메인 참조 라우팅

- 중고거래·Favorite·중고 신고·회원 탈퇴 연계·찜/조회수/이미지 카운터가 포함되면
  `.claude/skills/references/used-favorite-review.md`를 처음부터 끝까지 읽고 적용한다.
- 결제·정산·PortOne은 `payment-settlement.md`를 적용한다.
- 참조 문서는 최소 기준이다. 목록에 없는 경쟁 진입점과 계약도 직접 도출한다.

### 재리뷰 완료 조건

- 범위 원장에 있는 이전 지적을 `해결 / 잔존 / 사용자 승인 / 보류 / 제외`로 분류한다.
- 수정으로 새로 추가된 DTO, 쿼리, 필터, 락, 인덱스, 운영 DDL과 테스트를 다시 리뷰한다.
- 새 지적은 `[회귀 / 이전 누락 / 범위 밖 기존 / 정책 보류]` 출처를 표시한다.
- `범위 밖 기존`은 차단 심각도 목록과 분리하고, 사용자가 범위 확대를 요청하기 전에는
  "이번 수정 후에도 남은 문제"처럼 표현하지 않는다.
- 다른 전문 리뷰어와 같은 원인을 보고하면 병합하되, 영향이 다른 문제를 하나로 뭉개지 않는다.
- 정적 리뷰만 수행했다면 "수정사항 없음"을 런타임 안전성 보증처럼 표현하지 않는다.
- 테스트 미실행, 외부 계약 미확인, 운영 조건 의존 항목을 명시한다.

## 외부 API 계약

- 외부 API 연동 코드는 공식 최신 문서를 1차 자료로 사용해 method, path, header, body,
  응답 wrapper, 상태 enum, 멱등성, 테스트/운영 차이를 대조한다.
- 공식 계약이 최근 변경될 수 있으므로 기억이나 기존 주석만으로 통과시키지 않는다.
- 외부 API Mock이 현재 인터페이스대로 응답한다는 사실은 실제 계약 준수 근거가 아니다.
- 요청·응답을 수동 Map/JsonNode로 구성하는 코드는 필수 필드와 wrapper 위치를 모두 확인한다.
- 결제·정산·PortOne 리뷰는 `.claude/skills/references/payment-settlement.md`를 반드시 읽는다.
- 공식 문서에서 확인할 수 없는 항목은 "추가 확인 필요"로 분리하고 추측으로 단정하지 않는다.

## 심각도 기준

### 🔴 Critical — 즉시 수정 필요

- 권한/소유권 검증 누락
- 다른 사용자 리소스 접근 가능
- 결제/주문/재고 정합성 깨짐
- 환불/취소 순서 오류로 금전 피해 가능
- Entity 직접 반환으로 민감 정보 노출
- 인증 없이 보호 API 접근 가능
- 운영 데이터 삭제 위험

### 🟠 Major — 머지 전 수정 필요

- `@Transactional` 누락
- `@Transactional(readOnly = true)` 누락
- Request DTO Validation 누락
- `ApiResponse<T>` 미사용
- ErrorCode 부적절
- Entity 규칙 위반
- public API 응답 구조 변경
- Page/Slice/정렬 방식 변경
- 도메인 이벤트 대신 FCM/SSE 직접 호출

### 🟡 Minor — 개선 권장

- Swagger 어노테이션 누락
- 네이밍이 다소 불명확하지만 동작 영향 없음
- 중복 조회 가능성
- N+1 가능성
- 불필요한 import
- 테스트 보완 필요

## 출력 형식

위반 사항만 심각도별로 보고한다.

### 🔴 Critical

- `파일:라인` 위반 내용 1줄
    - 수정 방향 1줄

### 🟠 Major

- `파일:라인` 위반 내용 1줄
    - 수정 방향 1줄

### 🟡 Minor

- `파일:라인` 위반 내용 1줄
    - 수정 방향 1줄

위반이 없으면 아래 형식으로만 출력한다.

```text
✅ [영역명] 표준 준수 — 점검 항목 N개 통과
```

## 출력 원칙

- 위반 사항만 출력한다.
- 긴 설명을 하지 않는다.
- 긴 코드 인용을 하지 않는다.
- 같은 원인의 반복 위반은 하나로 묶는다.
- 추측이면 "추가 확인 필요"라고 표시한다.
- 수정 방향은 한 줄로 제시한다.
- 코드 변경을 수행했다는 표현을 사용하지 않는다.
