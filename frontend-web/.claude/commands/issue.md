지금 브랜치에서 한 작업("$ARGUMENTS"가 있으면 그 범위, 없으면 이 대화에서 지금까지 한 작업 전체)을 이음 이슈 템플릿으로 작성하세요. `/new-branch`로 시작했는지 여부와 무관하게, 아무 브랜치에서나 독립적으로 쓸 수 있다.

## 절차

1. 작업이 다 됐다고 판단되면 곧바로 문서를 쓰지 말고, 먼저 사용자에게 짧게 확인받는다 (예: "여기까지 하면 될 것 같은데 맞을까요?" 식으로, 실제로 뭘 했는지 요약과 함께). 사용자가 OK 하기 전에는 진행하지 않는다.
2. 사용자가 OK하면, 실제로 뭘 수정했는지 정확히 파악한다 — `git status`, `git diff`(또는 커밋까지 됐다면 `git diff develop...HEAD --stat`)로 실제 변경 파일을 확인한다. 대화 기록에 의존하지 말고 반드시 git으로 재확인한다 — 기억과 실제 디스크 상태가 어긋날 수 있다.
3. 아래 템플릿 그대로 작성해서 채팅에 보여준다:

```markdown
[{구분}] {작업 내용 한 줄 요약}

## 📄 작업 유형
- [ ] 기능 개발
- [ ] 화면 개발
- [ ] API 개발
- [ ] 문서 수정
- [ ] 버그 수정
- [ ] 리팩토링
- [ ] 테스트

## 🎯 작업 목적
<!-- 이 작업을 수행하는 이유를 작성합니다. -->

## 📌 작업 내용
<!-- 구현하거나 수정할 내용을 구체적으로 작성합니다. -->
-
-
-

## ✅ 완료 조건
<!-- 작업 완료 여부를 판단할 수 있는 기준을 작성합니다. -->
- [ ]
- [ ]
- [ ]

## 🔗 관련 문서 / API
<!-- 관련된 SDD, API 명세, 화면 설계서, Notion 링크 등을 작성합니다. -->
-

## 📎 참고 사항
<!-- 주의해야 할 점이나 공유할 내용을 작성합니다. -->
-
```

## 작성 규칙

- 제목의 `{구분}`은 현재 브랜치 타입과 맞춘다 (`fix/...` 브랜치 → `[fix]`, `feat/...` 브랜치 → `[feat]`) — 이 저장소 커밋/PR 제목 표기(`[feat] 사장 메인 대시보드 API 연동` 등)와 동일한 스타일로 쓴다. 브랜치명으로 판단하기 애매하면 사용자에게 묻는다.
- 작업 유형 체크박스는 실제로 한 작업에 맞게 체크한다 (복수 선택 가능, 나머지는 빈 채로 둔다).
- 작업 내용은 실제로 수정한 파일/로직 단위로 구체적으로 적는다 — "버그 고침" 같은 뭉뚱그린 문장 금지.
- 완료 조건은 실제로 검증한 것만 적고, 검증된 항목은 `[x]`로 체크한다. 검증 안 하고 추측만 한 건 빈 `[ ]`로 남긴다.
- 참고 사항에는 나중에 이 변경을 보는 사람이 헷갈릴 만한 트레이드오프·제약·알려진 한계를 적는다.

## 마무리

문서를 보여준 뒤에는 파일로 저장할지 물어본다. 저장한다면 어느 경로에 둘지도 같이 물어본다 — 이 저장소에 `docs/ai-manager/issues/`처럼 주제별 폴더가 이미 있으면 참고하되, 이번 작업 주제에 맞는 폴더가 없으면 임의로 새 폴더를 만들지 말고 사용자에게 위치를 확인한다.

커밋/푸시/PR 생성은 이 커맨드의 범위 밖이다 — 사용자가 직접 한다.
